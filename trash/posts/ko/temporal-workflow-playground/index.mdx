파일을 변환하고, 결과를 저장하고, 알림을 보냅니다. 그런데 변환이 끝나기 전에 워커가 멈추면 어떻게 될까요? 이 글에서는 **작업을 실행하는 주체와 진행을 기억하는 주체**를 나누어 살펴봅니다.

## 먼저 구분할 세 가지 역할

**Temporal 서비스는 진행을 보관합니다.** 실행 히스토리와 태스크 큐, 타이머를 관리합니다. 예시의 이미지 변환 코드를 직접 실행하는 주체는 워커입니다.

**워크플로 워커는 순서와 분기를 실행합니다.** “이미지를 변환한 뒤 결과를 저장한다”는 흐름을 코드로 표현하고, 액티비티 실행 같은 명령을 서비스에 전달합니다.

**액티비티 워커는 외부 작업을 수행합니다.** HTTP 호출, 파일 변환, DB 저장처럼 실패할 수 있는 일을 담당합니다. 한 프로세스가 두 종류의 태스크를 함께 처리할 수도 있습니다. 그림은 역할을 구분하기 위해 나누었습니다.

## 실패한 액티비티는 어떻게 다시 실행될까?

그림에서 **실패 후 재시도**를 선택하면 이미지 변환의 첫 시도가 실패합니다. 서비스는 재시도 가능한 오류인지, 정책과 시간 제한이 다음 시도를 허용하는지에 따라 다시 예약합니다.

이때 같은 워크플로 안에서 액티비티의 다음 시도가 이루어집니다. 이미 성공한 모든 작업을 처음부터 다시 수행한다는 뜻은 아닙니다.

> **재생과 재시도는 다릅니다.** 워크플로 재생은 기록된 히스토리를 바탕으로 워크플로 상태를 재구성하는 과정입니다. 액티비티 재시도는 외부 작업을 다시 수행하는 것입니다. 이 페이지의 실패 시나리오는 액티비티 재시도를 보여줍니다.

그림 옆의 ‘설명용 실행 기록’은 이해를 돕기 위한 요약입니다. 실제 Event History의 이벤트 목록과 일대일로 대응하지 않습니다. 특히 재시도 중인 액티비티의 중간 실패마다 `ActivityTaskFailed` 이벤트가 남는 것은 아닙니다.

## 재시도가 해결하지 않는 것

예를 들어 외부 서비스에는 저장이 성공했지만 응답을 받기 전에 연결이 끊길 수 있습니다. 이 경우 다시 실행하면 같은 데이터가 두 번 생성될 수 있습니다. **같은 요청을 여러 번 처리해도 결과가 중복되지 않도록 멱등성을 설계해야 합니다.**

또한 무한히 기다릴 수는 없습니다. 재시도 횟수와 간격뿐 아니라 액티비티의 타임아웃, 업무에서 허용하는 전체 시간도 함께 정해야 합니다. 위 계산기는 대기 시간만 분리해 보여줍니다.

## 직접 확인할 질문

- ‘실패’ 단계에서도 워크플로가 같은 실행으로 이어지는가?
- 재시도에서 실제로 다시 일하는 주체는 누구인가?
- 증가 배수를 1로 바꾸면 대기 시간은 어떻게 달라지는가?
- 최대 대기 시간에 도달한 뒤에도 간격이 계속 늘어나는가?
