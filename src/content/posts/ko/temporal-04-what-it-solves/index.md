## 개요

### 앞 편에서 배운 것

1. [1편](/posts/temporal-01-overview/): 공연 예매 흐름이 중간에 멈출 수 있는 세 지점과, Temporal이 진행을 기록해 멈춘 곳부터 이어 가는 방식을 봤다.
2. [2편](/posts/temporal-02-execution-model/): 예매 예제를 서버 다섯 개로 나눠 구성 요소가 어떤 순서로 일하는지와, 재생이 되기 위한 조건을 봤다.

### 이번 편에서 배울 것

앞 편은 Temporal이 「어떻게 동작하는가」를 봤다. 이번 편은 그 기능으로 **무엇이 해결되고 무엇이 개발자에게 남는지** 정리한다.

1. 1편에서 직접 구현하려면 만들어야 한다고 적은 다섯 가지를 Temporal이 맡는 것과 개발자에게 남는 것으로 나누고, 1편의 세 멈춤 지점에 적용해 본다. 재시도 정책과 기다리는 업무를 표현하는 방법(타이머·Signal)도 이 안에서 본다.
2. 여러 서비스를 조정하는 코드를 어디에 둘지에 대한 나의 설계 관점을 적는다.
3. 도입할 때 함께 맡게 되는 운영 책임과 도입 판단 기준을 본다.

### 이 글의 전제와 용어

1. **예매 예제**: 관람객이 예매를 요청하면 예매 서비스가 좌석 임시 확보(10분 유지) → 결제 승인 → 좌석 확정 → 티켓 발급을 차례로 다른 서비스에 요청한다. 예매 서비스는 이 순서를 Workflow로, 각 서비스 호출을 Activity로 만들어 Worker에서 실행한다고 가정한다. [2편](/posts/temporal-02-execution-model/)의 서버 구성에서는 `booking-worker`가 이 Worker다.
2. **용어**: Workflow는 업무의 순서를 적은 코드, Activity는 외부 호출 같은 한 단계의 코드, Worker는 그 코드를 실행하는 우리 서버의 부분이다. 재생(replay)은 Worker가 바뀌었을 때 기록된 이력으로 Workflow 코드를 다시 실행해 멈춘 지점까지 상태를 되살리는 과정이다. Workflow ID는 개발자가 정하는 실행의 이름이고, Run ID는 실행할 때마다 Temporal이 새로 붙이는 고유 값이다. Activity ID는 Workflow 안의 Activity 호출마다 붙고 재시도해도 바뀌지 않는다.

## Temporal이 해결하는 것과 해결하지 못하는 것

Temporal이 책임지는 범위는 **Temporal의 실행 이력(Event History)에 기록된 사실**까지다. 어떤 단계의 완료가 이력에 있으면 Temporal은 그 단계를 다시 실행하지 않고 다음 단계로 넘어간다. 완료 기록이 없으면, 그 단계가 외부 서비스에서 실제로 처리됐더라도 Temporal은 그 사실을 모른다. 아래 두 목록은 이 경계에서 나뉜다.

### Temporal이 대신 해 주는 일

1편에서 [직접 구현하려면 만들어야 한다고 적은 다섯 가지](/posts/temporal-01-overview/#정상-흐름보다-어려운-것은-중단-이후다) 가운데 1~~3번(진행 상태 저장, 멈춘 업무 이어 가기, 재시도)은 Temporal이 맡는다. 아래 목록의 1~~3번이 그것이다. 4·5번(대기 상태 보존, 중복 시작 방지)은 Temporal이 더해 주는 일이다. 1편 목록의 4·5번(중복 처리 방지, 마무리 규칙)은 다음 절의 「개발자에게 남는 일」로 간다.

1. **어디까지 끝났는지 기록한다.** Workflow 시작, Activity 완료와 그 결과, 타이머 만료가 Event History에 남는다. 진행 상태를 담을 테이블을 따로 설계하지 않아도 된다. 다만 예매·좌석·티켓 같은 업무 데이터는 여전히 각 서비스의 DB에 저장한다.
2. **멈춘 업무를 이어 간다.** Worker가 종료되면 다른 Worker가 이력을 재생해 기록된 다음 단계부터 실행한다. 멈춘 요청을 주기적으로 찾아 다시 실행하는 복구 배치를 따로 만들지 않아도 된다. Worker 프로세스를 띄우고 배포하는 일은 여전히 우리 팀이 한다.
3. **실패한 Activity를 정해 둔 정책대로 다시 실행한다.** 재시도 정책에는 다음 시도까지의 간격, 간격을 늘리는 비율, 최대 간격, 최대 횟수, 재시도하지 않을 오류를 지정한다. 아무것도 지정하지 않으면 Activity는 1초 간격에서 시작해 간격을 2배씩 늘리되 100초를 넘기지 않고, 성공할 때까지 횟수 제한 없이 다시 시도한다. Schedule-To-Close 타임아웃(재시도를 포함한 전체 실행 시간)을 정하면 그 시간 안에서만 다시 시도한다. 정책을 정해 두면 기다렸다가 다시 실행하는 일은 Temporal이 한다. Activity 재시도와 Workflow 실행 전체의 재시도는 서로 다른 설정이다. ([재시도 정책](https://docs.temporal.io/encyclopedia/retry-policies))
4. **기다리는 동안 진행 상태를 잃지 않는다.** 업무에는 지금 실행할 일만 있는 것이 아니다. “10분 뒤 결제 결과를 다시 조회한다”나 “관리자 승인을 기다린다”처럼 기다리는 일도 있다. Temporal은 이것을 두 가지로 표현한다.
   1. **영속 타이머**: Workflow가 기다릴 시간을 이력에 기록한다. Worker 프로세스가 살아서 시간을 세지 않아도 되고, 기다리는 사이 Worker가 바뀌어도 이어 간다. 다만 타이머가 만료된 시각에 다음 코드가 바로 실행된다는 뜻은 아니다. 그 일을 가져갈 Worker가 떠 있어야 하고 작업 지연도 영향을 준다. ([타이머와 대기](https://docs.temporal.io/workflow-execution/timers-delays))
   2. **Signal**: 실행 중인 Workflow에 승인·취소 같은 새 정보를 전달하는 메시지다. Workflow가 Signal을 기다리도록 작성하면, Signal이 올 때까지 기다렸다가 그 정보를 반영해 다음 단계로 간다. Signal이 접수됐다는 것과 그 요청에 따른 처리가 끝났다는 것은 다른 사실이다. ([Java SDK 메시지 전달](https://docs.temporal.io/develop/java/workflows/message-passing))
5. **같은 업무가 동시에 두 번 실행되지 않게 한다.** 예매 요청마다 고유한 값을 Workflow ID로 쓰면, 같은 ID의 Workflow가 실행 중일 때 새 실행은 시작되지 않는다. 다만 어떤 값을 ID로 쓸지는 개발자가 정한다. 관람객이 같은 요청을 두 번 보내도 같은 값이 나와야 하므로, 화면이 만든 요청 ID처럼 요청마다 고정된 값을 쓴다. 이미 끝난 Workflow와 같은 ID로 다시 시작하는 것은 기본 설정에서 허용되므로, 그것까지 막으려면 ID 재사용 정책도 정해야 한다. 이 검사는 끝난 실행의 기록이 남아 있는 보존 기간 안에서만 동작한다. ([Workflow ID와 중복 시작](https://docs.temporal.io/workflow-execution/workflowid-runid))

### 개발자에게 남는 일

다음은 Temporal을 도입해도 개발자가 설계해야 한다. 모두 **Temporal 밖에서 일어나는 일**이거나 **업무 규칙**이다.

1. **외부 서비스가 같은 요청을 두 번 처리하지 않게 한다(멱등성).** 2편 [재생의 조건과 Activity가 다시 실행되는 경우](/posts/temporal-02-execution-model/#재생의-조건과-activity가-다시-실행되는-경우)에서 본 것처럼 Activity는 두 번 이상 실행될 수 있다. 이때 두 번 결제되지 않게 막는 것은 결제 서비스다. 보통 다음 순서로 만든다.
   1. Activity가 재시도해도 바뀌지 않는 멱등 키를 만든다. Temporal 문서는 Workflow Run ID와 Activity ID를 합친 값을 예로 든다.
   2. 결제 요청에 그 키를 함께 보낸다.
   3. 결제 서비스는 이미 처리한 키로 요청이 오면 결제를 다시 하지 않고 처음 결과를 돌려준다.

   같은 Workflow ID로 실행을 새로 시작할 때뿐 아니라, Workflow 재시도·Continue-As-New·Reset으로 새 실행이 만들어질 때도 Run ID가 바뀌어 키가 달라진다. 결제처럼 예매 하나에 한 번만 일어나야 하는 일이라면 예매 ID 같은 업무 값으로 키를 만드는 방법도 검토한다. 결제 서비스나 외부 결제 대행사가 멱등 키를 지원하지 않으면, 결제 전에 기존 결제 내역을 조회하는 방식 등을 따로 설계해야 한다. ([Activity와 멱등성](https://docs.temporal.io/activity-definition))

2. **결과를 모르는 단계를 확인하는 방법을 정한다.** 응답을 받지 못한 결제가 실제로 됐는지는 결제 서비스에 물어봐야만 알 수 있다. 조회 API가 있으면 “확인 중인 결제를 일정 간격으로 조회하다가 결과를 받으면 다음 단계로 간다”는 흐름은 앞의 재시도나 타이머로 표현할 수 있다. 조회 API가 있는지, 몇 번까지 조회하고 언제 사람에게 넘길지, 늦게 도착한 승인 결과를 어떻게 처리할지는 개발자가 정한다.
3. **다시 시도할 실패와 멈출 실패를 나눈다.** 연결이 잠깐 끊긴 실패는 다시 시도하면 풀릴 수 있다. 카드 거절은 몇 번을 다시 시도해도 결과가 같다. 앞에서 본 것처럼 Activity의 기본 재시도 정책은 횟수 제한이 없고 재시도하지 않을 오류도 지정돼 있지 않다. 그대로 두면 카드 거절을 오류로 던졌을 때 그것도 계속 다시 시도한다. 그래서 어떤 오류를 재시도하지 않을지 개발자가 지정한다. 재시도 간격·횟수·타임아웃의 값도 개발자가 정한다. ([재시도하지 않을 오류](https://docs.temporal.io/encyclopedia/retry-policies))
4. **이미 끝난 일을 되돌리는 방법(보상)을 정한다.** 결제 승인 뒤 티켓을 끝내 발급하지 못하면 결제를 취소할지, 티켓 발급을 계속 시도할지 정해야 한다. 보상은 여러 DB를 한꺼번에 원래 상태로 돌리는 rollback과 다르다. 취소 요청도 실패할 수 있어 그 결과를 다시 확인해야 한다. 보상 코드를 Workflow에 작성하면 Temporal이 실행해 주지만, 무엇을 어떤 순서로 되돌릴지는 업무 규칙이다. ([Saga와 보상](https://temporal.io/blog/saga-pattern-made-easy))
5. **무엇이 끝나야 「완료」인지 정한다.** 결제가 승인됐다는 사실만으로 예매가 끝난 것은 아니다. 좌석 확정과 티켓 발급까지 끝나야 예매 완료로 볼지 애플리케이션이 정한다.

### 1편의 세 멈춤 지점에 적용해 보기

[1편 그림 1-1~1-3](/posts/temporal-01-overview/#가상의-예제-공연-예매-서비스)의 예매 서비스가 Worker를 실행한다고 가정한다. 결과는 종료가 Activity의 완료 보고 뒤에 일어났는지, 앞에 일어났는지에 따라 갈린다. 보고 뒤라면 다음 단계부터 이어 가고, 보고 전이라면 그 Activity를 다시 실행한다.

1. **그림 1-1, 좌석 확보 뒤 종료**: 좌석 확보의 완료가 기록됐다면 새 Worker가 결제 단계부터 이어 간다. 여기까지는 Temporal이 해결한다. 남는 일은 둘이다. 좌석이 10분 뒤 풀리기 전에 이어 갈 수 있는지는 Worker가 언제 다시 뜨는지에 달려 있다. 그래서 이미 풀렸을 때 다시 확보할지, 예매를 실패로 끝낼지 개발자가 정한다. 또 완료 보고 전에 종료됐다면 좌석 확보가 다시 실행되므로 좌석 서비스도 같은 요청을 알아봐야 한다.
2. **그림 1-2, 결제 응답 전 종료**: Temporal만으로는 해결되지 않는다. 결제 완료가 기록되지 않았으므로, Temporal은 Start-To-Close 타임아웃이나 Heartbeat 타임아웃이 지나 실패로 판단한 뒤 결제 Activity를 다시 실행한다. Temporal이 맡는 것은 그 재시도를 정책대로 실행하는 일까지다. 두 번 결제되지 않는 것은 결제 서비스의 멱등 처리에 달려 있다.
3. **그림 1-3, 좌석 확정 뒤 종료**: 결제와 좌석 확정의 완료가 기록됐다면 새 Worker는 결제를 다시 하지 않고 티켓 발급부터 이어 간다. Temporal이 해결하는 경우다. 티켓 발급이 계속 실패할 때 결제를 취소할지는 개발자가 보상 규칙으로 정한다.

아래 표는 「Temporal이 해결하는 것과 해결하지 못하는 것」의 내용을 예매 예제에 맞춰 정리한 것이다.

| 필요한 일             | Temporal이 하는 것                 | 개발자가 하는 것                                |
| --------------------- | ---------------------------------- | ----------------------------------------------- |
| 진행 상태 기록        | 단계별 완료를 Event History에 기록 | 업무 데이터를 각 서비스 DB에 저장               |
| 멈춘 업무 이어 가기   | 이력을 재생해 다음 단계부터 실행   | Worker 실행·배포                                |
| 실패한 단계 재시도    | 정책대로 기다렸다가 다시 실행      | 간격·횟수·타임아웃, 재시도하지 않을 오류를 지정 |
| 타이머·승인 대기      | 타이머와 받은 Signal을 이력에 보존 | 기다릴 시간과 기한이 지났을 때의 처리           |
| 같은 업무의 중복 시작 | 실행 중인 같은 Workflow ID를 거부  | ID로 쓸 값, 끝난 ID의 재사용 정책               |
| 외부 서비스 중복 처리 | 없음                               | 멱등 키와 외부 API 계약                         |
| 결과를 모르는 단계    | 없음                               | 조회 방법과 횟수, 사람에게 넘길 기준            |
| 이미 끝난 일 되돌리기 | 작성한 보상 코드 실행              | 무엇을 어떤 순서로 되돌릴지                     |
| 예매 완료 판정        | 없음                               | 무엇이 끝나야 완료인지                          |

## DDD 관점에서 보는 서비스 간 조정 — 나의 설계 관점

DDD에서는 도메인의 규칙과 모델을 명확한 경계 안에 두고, 외부 시스템의 기술적인 세부 사항이 도메인 모델에 직접 섞이지 않도록 설계한다. 그렇다고 서비스 간 협력 자체가 잘못된 것은 아니다. 여러 서비스가 함께 수행하는 업무에는 호출 순서와 대기·실패 처리를 조정하는 코드가 필요하다. ([도메인 계층과 애플리케이션 계층의 책임](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice))

내가 DDD를 적용하면서 고민한 것도 이 조정 코드를 어디에 둘 것인가였다. 예매에서는 좌석 확보 가능 여부와 결제 취소 가능 여부를 각각 담당 서비스가 판단하고, Workflow는 어떤 순서로 요청하고 기다리며 실패에 대응할지를 관리하도록 나눌 수 있다. 나는 이런 서비스 간 조정을 업무별 Workflow에 모으면 흐름을 파악하고 변경하기 쉬울 것으로 본다. 이는 이 연재에서 이후 예매 예제로 검토할 설계 방향이며, Temporal이 도메인 경계를 자동으로 지켜 준다는 뜻은 아니다.

Facade가 여러 기능을 단순한 인터페이스로 제공한다면, 여기서 필요한 조정은 실행 순서·대기·실패 후 진행까지 다룬다. 따라서 Facade와 동일한 패턴으로 단정하지 않고, 서비스 간 업무 흐름을 조정하는 역할로 설명하겠다. 각 서비스의 내부 규칙까지 하나의 Workflow에 몰아넣지 않는 것이 중요하다. 이 조정 코드는 Temporal Server 내부가 아니라 우리가 운영하는 Worker에서 실행된다. ([Temporal의 실행 구조](https://docs.temporal.io/encyclopedia/architecture/how-temporal-works))

## 운영 방식과 이력에 남길 데이터도 정해야 한다

업무 규칙 쪽에서 개발자에게 남는 일은 앞의 [Temporal이 해결하는 것과 해결하지 못하는 것](#temporal이-해결하는-것과-해결하지-못하는-것)에서 정리했다. 여기서는 도입할 때 함께 맡게 되는 운영 쪽 책임을 본다.

먼저 운영 주체를 정해야 한다. Temporal Service를 직접 운영할 수도 있고 Temporal Cloud를 사용할 수도 있다. Cloud를 이용하면 Service 운영을 맡길 수 있지만, 일반적인 구성에서 업무 코드를 실행하는 Worker와 그 코드의 배포·외부 시스템 접근은 여전히 사용자가 관리한다. ([자체 운영과 Cloud](https://docs.temporal.io/temporal))

기록이 영속적으로 남는다는 점은 저장할 데이터를 검토해야 한다는 뜻이기도 하다. Activity 입력·결과 등 이력에 남는 자료의 크기와 민감정보를 고려해야 한다. 실행 이력에도 제한이 있으므로 아주 오래 실행되는 업무는 이력을 나누는 방법까지 검토하게 된다. ([이력과 제한](https://docs.temporal.io/workflow-execution/event))

이런 특성을 기준으로 보면, 긴 대기와 여러 외부 작업의 재시작 복구를 반복 구현하는 시스템에서 Temporal을 검토할 이유가 생긴다. 반대로 짧은 단일 DB 트랜잭션이나 기존 작업 큐로 요구를 충족한다면 추가 구성과 학습·운영 비용이 더 클 수 있다. 이는 이 글의 도입 판단 기준이며, 특정 규모부터 반드시 유리하다는 성능 측정 결과는 아니다.
