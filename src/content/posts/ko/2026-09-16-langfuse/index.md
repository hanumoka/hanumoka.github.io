이 글은 **Langfuse**가 무엇인지만 정리한다. 발음은 **랭퓨즈**다. LLM 앱을 만들어 점수를 내는 글이 아니다.

끝까지 읽으면 셋이 된다.

1. 왜 일반 로그와 APM만으로는 LLM 요청을 못 따라가는지 말할 수 있다.
2. 트레이스, 옵저베이션, 세션이 각각 무엇을 묶는지 가리킬 수 있다.
3. 랭퓨즈가 하는 일 셋을 구분한다. 관측, 프롬프트 관리, 평가.

근거는 공식 문서 [Langfuse Overview](https://langfuse.com/docs)와 [Observability](https://langfuse.com/docs/observability/overview), [데이터 모델](https://langfuse.com/docs/observability/data-model)이다. 이 글을 쓰는 시점에 랭퓨즈 계정을 만들어 추적해 보지 않았다. 코드 예는 문서에 있는 형태다.

## 목차

## 이 글에서 쓰는 말

- **LLM**: 큰 언어 모델. 텍스트를 받아 텍스트를 생성하는 모델이다. ChatGPT 같은 서비스 뒤에 있는 계산기다.
- **프롬프트**: 모델에 보내는 입력 문장. 시스템 지시와 사용자 말이 여기에 들어간다.
- **토큰**: 모델이 읽고 쓰는 조각 단위. 과금과 길이 제한이 보통 토큰으로 센다.
- **관측성**: 밖으로 나온 기록만 보고 안에서 무슨 일이 있었는지 아는 능력. 로그, 메트릭, 트레이싱을 묶는 말이다.
- **트레이싱**: 한 요청이 지나간 단계를 인과 관계째로 남기는 기법.

## 왜 로그 파일만으로는 부족한가

Spring 앱은 같은 입력에 같은 코드면 같은 결과가 나온다. 실패하면 스택 트레이스와 SQL 로그로 줄을 찾는다.

LLM 앱은 같은 프롬프트여도 답이 달라질 수 있다. 공식 문서가 비결정적이라고 부르는 자리다. 한 사용자 질문에 모델 호출이 여러 번 일어나고, 검색, 도구 호출, 재시도가 끼어든다. `log.info`로 문자열을 남기면 호출 사이의 관계가 끊긴다.

랭퓨즈는 그 한 번의 사용자 요청을 **한 덩어리**로 남긴다. 문서가 애플리케이션 트레이싱이라고 부르는 것이다. 남기는 것은 대략 이것이다.

- 보낸 프롬프트
- 모델이 돌려준 응답
- 토큰 사용량
- 지연
- 그 사이에 있던 도구 호출과 검색 단계

Micrometer가 지연과 처리량을 숫자로 모은다면, 랭퓨즈는 **그 숫자 뒤에 어떤 프롬프트가 있었는지**를 같이 본다.

## 데이터를 어떻게 묶는가

공식 데이터 모델은 셋이다.

| 이름           | 무엇을 묶는가                                                                |
| -------------- | ---------------------------------------------------------------------------- |
| **옵저베이션** | 한 단계. LLM 호출, 도구 호출, 검색 같은 것. 단계 안에 단계가 들어갈 수 있다. |
| **트레이스**   | 사용자 요청 하나. 같은 `trace_id`를 가진 옵저베이션의 묶음.                  |
| **세션**       | 여러 트레이스. 채팅처럼 말이 오가는 한 줄기.                                 |

채팅 한 턴이 트레이스 하나이고, 그 안의 모델 호출이 옵저베이션이다. 같은 대화창의 턴들을 세션으로 묶는다.

필터에 쓰는 라벨도 있다. 환경(`production` / `staging`), 태그, 사용자 ID, 메타데이터, 릴리스 버전. 문서는 이 값들이 트레이스 안의 옵저베이션에 복사되어 조회가 빨라진다고 적는다.

OpenTelemetry 위에 서 있다. 랭퓨즈 SDK만 쓰는 길이 있고, OpenTelemetry로 보낸 뒤 랭퓨즈와 Datadog에 같이 넣는 길도 있다.

전송은 요청을 막지 않는다. SDK가 메모리에 쌓아 두고 뒤에서 묶음으로 보낸다. 웹 서버처럼 오래 사는 프로세스면 그 전송이 스스로 돈다. 짧게 살고 끝나는 스크립트는 종료 전에 `flush()`를 호출해야 한다. 안 하면 버퍼에 남은 트레이스가 프로세스와 함께 사라진다. 이것도 문서의 경고다.

## 플랫폼이 하는 일 셋

관측만 있는 도구가 아니다. 문서가 나누는 기둥은 셋이다.

1. **관측**. 트레이스를 남기고, 비용과 지연을 본다.
2. **프롬프트 관리**. 프롬프트를 버전으로 두고, 코드 변경 없이 라벨로 배포한다. 화면에서 시험할 수 있다.
3. **평가**. 응답의 질을 점수로 붙인다. 사람 라벨, 사용자 피드백, 코드, 다른 LLM으로 채점하는 방법이 있다. 데이터셋을 만들어 실험할 수도 있다.

처음 배울 때는 1만 한다. 2와 3은 트레이스가 쌓인 다음이다.

일반 APM과의 차이는 문서가 이렇게 적는다. 랭퓨즈는 토큰, 모델 파라미터, 프롬프트/응답 쌍, 평가 점수를 처음부터 안다. 평가, 프롬프트 관리, 실험, 대시보드가 같은 제품 안에 있다. 오픈소스이고 직접 호스팅할 수 있다.

## 다음에 실습할 때 볼 코드

문서의 Python 빠른 시작은 OpenAI 호출을 감싸는 형태다. `langfuse.openai`로 클라이언트를 바꾸고, 함수에 `@observe()`를 붙인다.

```python
from langfuse import observe
from langfuse.openai import openai


@observe()
def story():
    return openai.chat.completions.create(
        model="gpt-4o-mini",
        max_tokens=100,
        messages=[
            {"role": "system", "content": "You are a great storyteller."},
            {
                "role": "user",
                "content": "Once upon a time in a galaxy far, far away...",
            },
        ],
    ).choices[0].message.content


@observe()
def main():
    return story()


main()
```

이 코드를 이 컴퓨터에서 실행해 보지는 않았다. 실제로 돌리려면 랭퓨즈 키와 OpenAI 키가 필요하고, 짧은 스크립트면 끝에 `flush()`가 필요하다.

실습의 완료 확인은 이것이다.

1. 함수를 한 번 호출한다.
2. 랭퓨즈 화면에 트레이스 한 건이 생긴다.
3. 그 안에 보낸 메시지와 받은 문장이 보인다.
4. 토큰과 지연이 비어 있지 않다.

## 여기서 하지 않은 것

- LLM을 직접 학습시키거나 가중치를 고치는 것.
- 랭퓨즈를 직접 호스팅하는 것.
- 평가 점수 파이프라인, 데이터셋 실험.
- 트리톤 위에 모델을 올리는 것. 트리톤은 모델을 **서빙**하는 서버고, 랭퓨즈는 호출 **기록**을 보는 도구다. 둘은 같은 층이 아니다.

오늘은 **한 요청을 트레이스로 남기는 이유와 이름**까지다. 그다음에 위 예제를 한 번 돌려 화면에서 그 요청을 찾으면 된다.
