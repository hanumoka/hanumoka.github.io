결론부터 말한다. **"좀 느리다"는 관측이 아니다.** 어떤 기계에서, 어떤 입력으로, 초당 몇 개를 처리했고, 그중 느린 쪽은 몇 밀리초였는지를 남겨야 측정이다.

처리량과 지연을 숫자로 남긴 기록이 없으면, 장애를 볼 때와 앞에서 말한 요청 경로·트랜잭션 경계를 설명할 때 같은 빈칸이 된다. 화면이 그려지는 속도를 잰 것과는 다른 칸이다.

## 이 글에서 쓰는 말

- **처리량**: 같은 조건에서 단위 시간당 끝난 요청 수. 초당 개수처럼 쓴다.
- **지연**: 요청 하나가 끝나기까지 걸린 시간.
- **백분위**: 예를 들어 100개 중 느린 쪽 5번째. "평균"만 보면 느린 요청이 숨는다.
- **측정 조건**: 머신, 데이터 크기, 동시 요청 수, 워밍업 여부. 이것이 없으면 숫자는 재현되지 않는다.

## 왜 평균만 쓰면 안 되는가

평균 50ms여도, 100개 중 5개가 2초면 사용자는 그 5개를 느리다고 느낀다. 그래서 지연은 **중간값**과 **느린 쪽(예: 95번째)** 을 같이 적는다. 여기 50ms와 2초는 예시일 뿐, 네가 잰 값이 아니다.

처리량은 "한 명이 연속으로 두드렸을 때"와 "스무 명이 동시에 두드렸을 때"가 다르다. 숫자를 적을 때 동시 수를 빼먹으면 그 숫자는 다른 날 다시 만들 수 없다.

## 최소로 재는 순서

도구 이름보다 순서가 먼저다.

1. 잴 대상 API 하나를 고른다. "시스템 전체"는 첫 측정이 아니다.
2. 조건을 적는다. CPU·메모리, 데이터 몇 건, 동시 몇 명, 몇 초 동안.
3. 같은 요청을 워밍업으로 몇 번 보낸다. 첫 요청은 보통 더 느리다.
4. 본 측정을 돌린다.
5. 처리량, 중간 지연, 느린 쪽 지연을 적는다.
6. 병목이 어디인지 **한 줄**로 적는다. 추측이면 추측이라고 적는다.

이 여섯이 한 모듈의 "측정 기록 1건"이다. 대시보드 스크린샷만 있고 조건이 없으면 기록이 아니다.

## 직접 해 보는 최소 실험

로컬에서만 해도 된다.

1. 주문 생성 API 하나를 고른다.
2. 동시 1명으로 30초 보낸다. 숫자를 적는다.
3. 동시 10명으로 30초 보낸다. 숫자를 적는다.
4. 둘을 비교한다. 처리량이 10배가 안 되면, 그 이유가 커넥션인지 락인지 로그인지 **다음 질문**이 된다.

도구는 부하 스크립트든, 간단한 반복 호출이든 상관없다. 닫히는 것은 "숫자를 남겼는가"이지 "무슨 제품을 썼는가"가 아니다.

## 이 글이 닫지 않는 것

- 관측 대시보드 설치
- 분산 추적
- 부하 테스트 도구 설정

관측 스택은 잴 대상이 생긴 뒤에 붙인다. 대상 없이 대시보드만 세우면 인프라만 남는다.
