이 글은 **Temporal**이 무엇인지만 정리한다. 발음은 **템포럴**이다. 클러스터를 설치하거나 워크플로를 짜는 글이 아니다.

끝까지 읽으면 넷이 된다.

1. Temporal이 큐·크론·`@Async`와 무엇이 다른지 말할 수 있다.
2. 워크플로, 액티비티, 워커, 태스크 큐, Temporal 서비스가 각각 무엇을 하는지 가리킬 수 있다.
3. 프로세스가 죽어도 이어서 도는 이유가 이벤트 히스토리와 재생임을 안다.
4. MSA에서 오케스트레이터와 실제 일을 하는 서비스를 태스크 큐로 나누는 이유를 안다.

근거는 공식 문서 [Understanding Temporal](https://docs.temporal.io/evaluate/understanding-temporal)과 [Event History](https://docs.temporal.io/encyclopedia/event-history), [Retry Policies](https://docs.temporal.io/encyclopedia/retry-policies)다. 이 글을 쓰는 시점에 이 컴퓨터에서 Temporal 서버를 띄워 보지 않았다. 코드 예는 문서에 있는 형태다.

## 목차

## 이 글에서 쓰는 말

- **워크플로**: 업무 순서 그 자체. 코드로 쓴다. 화면에서 상자를 이어 붙이는 도구가 아니다.
- **액티비티**: 바깥 세계와 닿는 한 단계. HTTP 호출, DB 쓰기, GPU 추론 요청처럼 실패할 수 있는 일.
- **워커**: 우리 프로세스 안에서 도는 폴링 클라이언트. Temporal 서버가 우리 코드를 실행하지 않는다. 워커가 실행한다.
- **태스크 큐**: 워커가 일을 가져가는 대기열 이름. 큐 이름이 같아야 워크플로와 액티비티가 만난다.
- **이벤트 히스토리**: 그 실행에서 일어난 일의 내구성 있는 기록. 죽으면 이 기록을 재생해 상태를 되돌린다.
- **내구성 있는 실행**: 실패·재시작이 있어도 그 실행이 끝까지 간다는 보장. 공식 문서가 Durable Execution이라고 부르는 것이다.

## 왜 `@Async`와 Redis 큐만으로는 부족한가

Spring에서 긴 일을 빼는 방법은 여럿이다.

- `@Async` — 같은 JVM의 스레드 풀. 프로세스가 죽으면 그 실행은 사라진다.
- `@Scheduled` — 시각이 되면 메서드를 부른다. 중간에 어디까지 했는지는 안 들고 있다.
- Redis 스트림·메시지 큐 — 메시지 한 건은 남는다. **여러 단계의 순서와 보상**은 앱이 따로 짜야 한다.

분석 한 건이 라이선스 예약 → 상태 변경 → GPU 추론 → 결과 저장 → 예약 확정처럼 **여러 서비스를 지나면**, 한 단계가 타임아웃 났을 때 어디서부터 다시 할지가 문제다. 큐만 있으면 "메시지 재처리"는 되지만 "3단계까지는 끝났고 4단계만 다시"는 히스토리가 없으면 직접 구현한다.

Temporal은 그 순서를 **워크플로 코드**로 두고, 각 단계의 완료를 서버가 기록한다. 워커가 죽으면 다른 워커가 히스토리를 재생해 마지막 성공 지점부터 이어 간다. 공식 문서의 비유는 자동 저장이다. 비유는 여기까지다. 실제 동작은 아래 순서다.

## 한 실행이 가는 길

1. 앱이 Temporal 클라이언트로 워크플로를 시작한다. 태스크 큐 이름을 같이 넘긴다.
2. Temporal 서비스가 워크플로 태스크를 그 큐에 넣는다.
3. 그 큐를 폴링하는 **워크플로 워커**가 코드를 실행한다. 코드가 액티비티를 호출하면, 워커는 액티비티를 직접 실행하지 않는다. 서비스에 명령을 보낸다.
4. 서비스가 액티비티 태스크를 큐에 넣는다.
5. **액티비티 워커**가 바깥 호출을 한다. 성공·실패가 히스토리에 남는다.
6. 워크플로 워커가 히스토리를 보고 다음 줄로 간다.

서버는 오케스트레이션과 기록만 한다. **업무 데이터와 모델 호출은 우리 인프라의 워커 안에서 돈다.**

Java 워커 등록은 문서가 이 형태다.

```java
WorkerFactory factory = WorkerFactory.newInstance(client);
Worker worker = factory.newWorker("my-task-queue");
worker.registerWorkflowImplementationTypes(SayHelloWorkflowImpl.class);
worker.registerActivitiesImplementations(new GreetActivitiesImpl());
factory.start();
```

큐 이름 `my-task-queue`가 시작 옵션의 큐와 같아야 한다. 다르면 태스크는 쌓이고 아무도 가져가지 않는다.

## 워크플로와 액티비티를 가르는 기준

워크플로 코드는 **결정적**이어야 한다. 같은 히스토리를 재생하면 같은 명령을 다시 내야 한다. 그래서 워크플로 안에서 직접 HTTP를 치거나 `Thread.sleep`을 쓰지 않는다. 대기는 `Workflow.sleep`처럼 Temporal이 아는 타이머를 쓴다. 난수·현재시각·네트워크는 액티비티로 뺀다.

액티비티는 실패를 전제로 한다. 기본 재시도는 지수 백오프이고, 최대 횟수 기본값은 무제한에 가깝다. 공식 문서가 그래서 **액티비티는 멱등**이어야 한다고 적는다. 같은 입력을 두 번 실행해도 결과가 같거나, 두 번째가 첫 번째를 덮어도 안전해야 한다.

워크플로 실행 자체는 기본적으로 재시도하지 않는다. 한 실행이 실패로 끝나면 그 실행은 끝난 것이다. 다시 돌리려면 새로 시작하거나, 정책으로 재시도를 명시한다.

긴 GPU 호출처럼 수분~수십 분이 걸리는 액티비티는 **하트비트**를 보낸다. 하트비트가 끊기면 워커가 죽은 것으로 보고 다른 워커가 이어 받는다. 하트비트 없이 긴 액티비티만 두면, 타임아웃까지 그 슬롯이 점유된다.

## MSA에서 큐를 나누는 이유

한 서비스가 워크플로와 모든 액티비티를 같이 실행할 수도 있다. 서비스가 여럿이면 보통 이렇게 가른다.

| 큐          | 누가 폴링하는가       | 무엇을 실행하는가              |
| ----------- | --------------------- | ------------------------------ |
| 워크플로 큐 | 오케스트레이터 서비스 | 순서와 분기만                  |
| 액티비티 큐 | 그 일을 소유한 서비스 | GPU 호출, 저장, 라이선스, 정리 |

초기에 오케스트레이터가 HTTP로 다른 서비스를 부르게 두면, 재시도와 타임아웃이 HTTP 클라이언트 설정과 Temporal 설정 두 곳에 생긴다. 그 패턴을 버리고, **액티비티 워커를 소유 서비스 안에 두는** 쪽이 흔하다. 워크플로는 큐 이름만 알고, 실제 호출은 그 서비스가 한다.

큐를 모델 군이나 도메인마다 더 쪼갤 수 있다. 정량 추론 큐와 문장 생성 큐를 나누면, 워커 수를 따로 조절한다. 한 큐에 긴 GPU 일과 짧은 DB 일을 섞으면 짧은 일이 길 일 뒤에 선다.

GPU 호스트가 여러 대일 때, 호스트 선택은 앱이 하고 **실패 시 다음 호스트는 Temporal 재시도의 attempt**에 묶을 수 있다. 재시도가 다음 서버로 돌아가게 해 두면, 앱 안에 순회 루프를 또 두지 않는다. 앞 글의 정적 host:port 목록과 같이 읽는 자리다.

## 넣지 말아야 할 것

이벤트 히스토리는 오래 남고, UI와 CLI로 열람한다. 그래서 워크플로 인자·메모·검색 속성에 **개인정보·고객 원문·시크릿**을 넣지 않는다. 식별자는 불투명한 ID만 넘기고, 본문은 우리 DB에서 읽는다.

토글 `temporal.enabled=false`로 서버를 꺼도, 이미 돌던 실행과 스케줄 정리 순서를 정하지 않으면 워커만 죽은 채 히스토리가 남는다. 끄는 절차는 기능 플래그와 별개다.

## 다음에 실습할 때

로컬에서 익히는 최소 순서는 공식 시작 안내를 따른다.

1. Temporal CLI로 로컬 서비스를 띄운다.
2. Java SDK로 워크플로 하나와 액티비티 하나를 등록한다.
3. 워크플로를 시작하고 Web UI에서 그 실행이 보이는지 확인한다.
4. 액티비티 워커를 잠시 죽인 뒤 다시 켠다. 실행이 이어서 끝나는지 본다.

SaaS·온프렘에 붙이기 전에 종이로 채울 것은 이것이다.

1. 워크플로 큐와 액티비티 큐 이름이 환경마다 같은가. 다르면 워커가 빈 큐를 폴링한다.
2. 긴 액티비티에 하트비트와 start-to-close 타임아웃이 있는가.
3. 액티비티가 멱등인가. 재시도가 기본이기 때문이다.
4. 히스토리에 ID만 들어가는가.
5. GPU 호출 실패가 Temporal 재시도로 다음 호스트에 가는가, 앱 루프와 이중으로 도는가.

재지 않은 처리량을 적지 않는다. 샤드 수·워커 동시성은 측정한 뒤에 올린다.

## 여기서 하지 않은 것

- Temporal Cloud와 직접 설치의 비용 비교.
- Nexus, Schedule, Update 같은 상위 API.
- Kubernetes 오퍼레이터 설치.
- 특정 제품의 워크플로 단계 목록.

오늘은 **이름이 가리키는 네 조각과, 큐가 서비스 경계를 대신하는 이유**까지다. 서버는 기록하고, 워커가 실행하고, 히스토리가 이어서 돌린다.
