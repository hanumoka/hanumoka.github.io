이 글은 **NVIDIA Triton Inference Server**가 무엇인지만 정리한다. 발음은 **트리톤**이다. 모델을 학습시키거나 GPU에 올려 재는 글이 아니다.

끝까지 읽으면 셋이 된다.

1. 트리톤이 하는 일과, 이름이 비슷한 다른 도구와 무엇이 다른지 말할 수 있다.
2. 요청 하나가 서버 안에서 어떤 순서로 움직이는지 손가락으로 가리킬 수 있다.
3. 다음에 실습할 때 무엇을 폴더에 두고, 어느 포트로 확인하는지 안다.

근거는 NVIDIA 공식 문서 [Triton Inference Server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/index.html)와 저장소 [triton-inference-server/server](https://github.com/triton-inference-server/server)다. 이 글을 쓰는 시점에 이 컴퓨터에서 트리톤을 띄워 보지 않았다. 명령은 문서에 적힌 형태다.

## 목차

## 이 글에서 쓰는 말

- **모델**: 입력을 받아 출력을 계산하도록 학습이 끝난 파일 묶음. 이미지 분류 모델이면 사진이 들어가고 클래스 점수가 나온다.
- **학습**: 데이터로 모델의 가중치를 바꾸는 단계. 오래 걸리고, 보통 오프라인에서 한다.
- **추론**: 이미 학습된 모델에 새 입력을 넣어 답을 받는 단계. 서비스가 사용자 요청마다 하는 일이다.
- **백엔드**: 트리톤이 모델 파일을 실제로 실행하는 엔진. PyTorch, ONNX, TensorRT, Python 같이 종류가 다르다.
- **모델 저장소**: 트리톤이 읽을 모델 폴더. 서버를 켤 때 경로를 넘긴다.

## 이름이 비슷한 것

**NVIDIA Triton Inference Server**와 **OpenAI Triton**은 다른 물건이다.

- NVIDIA 트리톤은 **추론 서버**다. 모델을 받아 두고 HTTP/gRPC로 호출한다.
- OpenAI Triton은 **GPU 커널을 쓰는 언어**다. NVIDIA가 만든 것이 아니다.

이 글은 NVIDIA 쪽만 말한다. 한국어로 트라이톤이라고 적는 글도 있으나, 제품 이름은 Triton이고 보통 트리톤으로 읽는다.

## 왜 이런 서버가 필요한가

백엔드 개발자가 API를 만들 때 Spring Boot가 하는 일과 같다. 업무 규칙을 자바 메서드로 짜 두고, HTTP로 받는다.

학습이 끝난 모델은 그 메서드와 비슷한 자리다. 다만 실행 방법이 프레임워크마다 다르다. PyTorch 파일, ONNX 파일, TensorRT 파일이 섞이면, 앱마다 로딩 코드를 따로 짜게 된다.

트리톤은 그 로딩과 호출을 **한 서버**로 모은다. 공식 문서의 한 줄은 이것이다. 여러 프레임워크의 모델을 띄우고, HTTP/REST나 gRPC로 추론 요청을 받는다. GPU가 있으면 쓰고, CPU만 있는 기계에서도 같은 이미지를 돌릴 수 있다. GPU가 필요한 모델 설정은 CPU-only에서 로드가 실패한다.

Spring에 비유하면 대략 이렇다.

| Spring 쪽에서 아는 것    | 트리톤에서 대응하는 것  |
| ------------------------ | ----------------------- |
| 프로세스를 띄운다        | `tritonserver`          |
| 컨트롤러가 HTTP를 받는다 | HTTP 8000, gRPC 8001    |
| 설정 파일                | 모델마다 `config.pbtxt` |
| Actuator health          | `/v2/health/ready`      |
| Micrometer               | 메트릭 포트 8002        |

비유는 여기까지다. 트랜잭션이나 JPA와는 맞지 않는다.

## 요청 하나가 가는 길

공식 문서의 구조는 이 순서다.

1. 클라이언트가 HTTP 또는 gRPC로 추론 요청을 보낸다. C API로 같은 프로세스에 붙는 길도 있다.
2. 트리톤이 모델 이름에 맞는 **스케줄러**로 보낸다. 모델마다 스케줄 방식이 다를 수 있다.
3. 스케줄러가 요청을 묶을 수 있다. 문서가 동적 배칭이라고 부르는 자리다. 여러 요청의 입력을 한 번에 백엔드로 넘긴다.
4. **백엔드**가 모델 파일로 계산한다.
5. 출력이 클라이언트로 돌아간다.

서버를 켠 뒤에는 모델 관리 API로 어떤 모델이 올라왔는지 조회할 수 있다. Kubernetes에 넣을 때는 준비/생존 엔드포인트와 메트릭을 쓴다.

## 모델은 폴더 규칙이 있다

트리톤은 아무 디렉터리나 훑지 않는다. `--model-repository`로 넘긴 경로 아래가 저장소다. 문서가 요구하는 최소 모양은 이렇다.

```text
model-repository/
  모델이름/
    config.pbtxt
    1/
      모델파일
```

- 맨 아래 숫자 폴더가 **버전**이다. `1`, `2`처럼 숫자여야 한다. `0`으로 시작하는 이름은 무시한다.
- `config.pbtxt`가 그 모델의 설정이다. 어떤 모델은 생략하고 자동 생성을 쓸 수 있다.
- 버전 폴더 안의 파일 이름은 백엔드가 정한다. ONNX는 기본이 `model.onnx`, Python은 `model.py`다.

이 규칙이 깨지면 서버 로그에 READY가 안 뜨고, 테이블에 모델이 없거나 실패 이유가 적힌다.

## 다음에 실습할 때 볼 명령

가장 쉬운 설치는 NVIDIA GPU Cloud의 Docker 이미지다. 문서의 흐름은 셋이다.

1. 예제 모델 저장소를 준비한다.
2. 서버 컨테이너를 띄운다. GPU가 있으면 `--gpus=1`, 없으면 그 플래그 없이 같은 이미지를 쓴다.
3. 호스트에서 준비 여부를 확인한다.

포트는 문서 기준 셋이다.

| 포트 | 하는 일          |
| ---- | ---------------- |
| 8000 | HTTP 추론과 상태 |
| 8001 | gRPC             |
| 8002 | 메트릭           |

준비 확인은 이 요청이다. 200이면 서버가 추론을 받을 수 있다.

```shell
curl -v localhost:8000/v2/health/ready
```

이미지 태그의 `<xx.yy>`는 연·월 버전이다. 글을 쓰는 시점의 문서 예에는 `26.07`이 보인다. **지금 이 기계에서 그 태그를 받아 실행해 보지 않았다.** 받을 때 NGC에서 실제 태그를 확인한다.

GPU가 없는 노트북에서 첫 실습을 하려면, GPU를 요구하지 않는 예제 모델만 고른다. GPU 전용 설정이 있는 모델은 로드가 실패한다.

## 여기서 하지 않은 것

- 모델을 학습시키는 것. 트리톤은 학습기가 아니다.
- TensorRT로 모델을 최적화하는 것.
- 동적 배칭 숫자를 재는 것. 재지 않은 처리량을 적지 않는다.
- Kubernetes 배포.
- OpenAI Triton 언어.

오늘은 **이름을 가리고, 요청 길을 말하고, 폴더와 포트를 아는 것**까지다. 그다음에 예제 저장소를 받아 `/v2/health/ready`가 200이 되는지를 보면 된다.
